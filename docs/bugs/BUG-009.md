# BUG-009: `"paused"` is an undocumented `InviteRun` status value

## Status: OPEN

## Title
`run_invite()` now sets `InviteRun.status = "paused"` in two scenarios (FloodWait abort and
pacing-limit stop), but `"paused"` is not listed in the status enum in `REPORT.md` or
`DESIGN.md`. API consumers and the operator UI have no documented meaning for this value.

## Environment
- `app/services.py` — `run_invite()` (lines ~224, ~264)
- `docs/REPORT.md` — CollectRun/InviteRun status values
- `docs/DESIGN.md` — §"Runs, jobs, and attempts"

## Steps to Reproduce
1. Create a source with participants. Create a target.
2. Run a collect run.
3. POST `/invite-runs` with `max_per_minute: 1` and 2+ eligible candidates **OR** configure
   `FakeTelegramClient.flood_on_user_ids` to trigger FloodWait on the first candidate.
4. Inspect `InviteRun.status` in the response.

## Expected
`status` is one of the documented values: `queued | running | succeeded | failed | cancelled`

Or, if `"paused"` is a legitimate new state, it must be documented in REPORT.md and DESIGN.md
with:
- What it means (run hit a limit and stopped early; can be re-triggered)
- What fields in `stats` accompany it (`pause_reason`, `flood_wait_seconds`)
- Whether/how the operator can resume

## Actual
```json
{ "status": "paused", "stats": { "pause_reason": "pacing_limit", ... } }
{ "status": "paused", "stats": { "pause_reason": "flood_wait", "flood_wait_seconds": 60, ... } }
```

Neither `"paused"` nor `pause_reason` / `flood_wait_seconds` appear in the documented API
contract.

## Impact
- The operator UI cannot correctly render a run in `"paused"` state because the status is
  undocumented — it will likely fall into an "unknown" rendering branch.
- Consumers parsing the `status` field against the documented enum will reject or mishandle
  `"paused"` responses.
- FloodWait visibility in the invite run detail (required by the DESIGN.md acceptance checklist:
  "FloodWait backoff is visible in invite run detail") relies on `pause_reason` and
  `flood_wait_seconds` — these need to be contractually specified.

## Severity / Priority
**Low / P3** — documentation gap; the underlying behavior (abort on FloodWait/pacing) is
correct and safe. The missing contract definition blocks UI implementation and operator
understanding.

## Fix Suggestion

1. Add `"paused"` to the status enum in `REPORT.md`:
   ```
   `status` values: `queued` | `running` | `succeeded` | `failed` | `cancelled` | `paused`
   ```

2. Document the new `stats` fields that accompany `"paused"`:
   ```
   pause_reason: "pacing_limit" | "flood_wait"
   flood_wait_seconds: integer (only when pause_reason = "flood_wait")
   ```

3. Update `DESIGN.md` §"Runs, jobs, and attempts" to include `paused` in the InviteRun status
   list and describe the resume flow (operator re-triggers the same target once the window
   resets or the FloodWait expires).
