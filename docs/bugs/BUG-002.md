# BUG-002: FloodWait does not pause or abort the invite run — loop continues

## Status: CLOSED — FIXED (2026-04-02)

`run_invite()` in `services.py` now catches `FloodWaitError`, records the failed attempt,
sets `run.status = "paused"` with `pause_reason = "flood_wait"` and `flood_wait_seconds`
in `run.stats`, then immediately returns — stopping all further candidate processing.

**Note**: The new `"paused"` status value is not yet documented in REPORT.md or DESIGN.md
(tracked as BUG-009).

---

## Title
When `FloodWaitError` is raised for a candidate, `run_invite` records the failure and immediately proceeds to the next candidate. The invite run never enters a paused/backoff state, and subsequent candidates are still attempted at full speed.

## Environment
- `app/services.py` — `run_invite()`
- `app/telegram_client.py` — `FloodWaitError`

## Steps to Reproduce
1. Create a source + target.
2. Collect 3 candidates (tg_user_ids: 10, 11, 12).
3. Configure `FakeTelegramClient.flood_on_user_ids = {10}` so user 10 raises FloodWaitError.
4. Start an invite run.
5. Inspect `fake_tg.invite_calls`.

## Expected
After FloodWaitError is raised for user 10, the run should:
- Record the failure with `error_code="flood_wait"`.
- Stop further invite attempts for the duration of the backoff (per `FloodWaitError.seconds`).
- Set run status to `failed` or a new `paused` state with a `resume_after` timestamp.

Users 11 and 12 must **not** be attempted during the backoff window.

## Actual
After FloodWaitError for user 10:
- Failure is recorded correctly.
- Users 11 and 12 are **still attempted immediately** — `invite_to_target` is called for them.
- Run finishes as `succeeded`.

```python
# services.py lines 217-230 — no break/return after FloodWaitError
except FloodWaitError:
    failed += 1
    code = "flood_wait"
    ...
    db.add(InviteAttempt(..., error_code=code))
# loop continues to next candidate  ← bug
```

## Impact
Telegram applies a FloodWait across the account; continuing attempts causes the client to receive longer bans and risks account suspension. This is explicitly called out as a hard requirement in DESIGN.md §"Rate limiting and anti-abuse" and SECURITY.md §"Rate limiting & backoff".

## Severity / Priority
**High / P1** — safety-critical; ignoring FloodWait can get the Telegram account banned.

## Fix Suggestion
Break out of the candidates loop (or re-raise a sentinel exception) when `FloodWaitError` is caught:
```python
except FloodWaitError as e:
    failed += 1
    failed_by_code["flood_wait"] = failed_by_code.get("flood_wait", 0) + 1
    db.add(InviteAttempt(..., error_code="flood_wait"))
    run.status = "failed"
    run.finished_at = utcnow()
    # optionally persist backoff_until = utcnow() + timedelta(seconds=e.seconds)
    break  # stop all further attempts
```
