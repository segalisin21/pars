# BUG-003: Pacing policy fields `max_per_minute` / `max_per_hour` are silently ignored

## Status: CLOSED — FIXED (2026-04-02)

`run_invite()` now reads `max_per_minute` and `max_per_hour` from the policy dict and enforces
them via monotonic-clock windows. When either limit is reached, the run immediately sets
`run.status = "paused"` with `pause_reason = "pacing_limit"` in stats and returns early.

**Implementation approach**: This uses a hard-stop (pause and return) rather than jittered
sleeps. DESIGN.md mentions "jittered pauses in production worker execution" — those are not
yet implemented. The current approach avoids blocking the API thread and is safe; the operator
must re-trigger the run once the time window resets.

---

## Title
`InvitePolicy.max_per_minute` and `max_per_hour` are validated by Pydantic and stored in `InviteRun.policy`, but `run_invite()` never reads or enforces them. All eligible candidates are invited at maximum system speed with no inter-request delay.

## Environment
- `app/services.py` — `run_invite()`
- `app/schemas.py` — `InvitePolicy`

## Steps to Reproduce
1. POST `/invite-runs` with `{"target_id": 1, "policy": {"max_per_minute": 1, "max_per_hour": 2, "cooldown_minutes": 0}}`.
2. Have 100 candidates ready.
3. Time the invite loop in a real run.

## Expected
The loop respects `max_per_minute=1` (≤1 invite per 60 s) and `max_per_hour=2` (≤2 total invites per hour), with jittered pauses as documented in DESIGN.md.

## Actual
All 100 candidates are invited in rapid succession. The `policy` dict in `run_invite`:
```python
cooldown_minutes = int(policy.get("cooldown_minutes", 1440))  # only this is read
```
`max_per_minute` and `max_per_hour` are **never read**.

## Impact
Without pacing, a real Telegram session will immediately trigger FloodWait and risk a permanent ban. This is listed as a **hard requirement** in DESIGN.md §"Rate limiting and anti-abuse" and SECURITY.md §"Rate limiting & backoff".

## Severity / Priority
**High / P1** — safety-critical for production use; together with BUG-002 creates a virtually guaranteed ban scenario.

## Fix Suggestion
In `run_invite`, track `invites_this_minute` and `invites_this_hour` counters, sleep between invites to respect the per-minute limit, and abort/pause when the per-hour ceiling is reached:
```python
max_per_minute = int(policy.get("max_per_minute", 2))
max_per_hour   = int(policy.get("max_per_hour", 30))
# After each successful invite:
#   time.sleep(60 / max_per_minute + jitter)
#   if invites_this_hour >= max_per_hour: break
```
