# BUG-005: API timestamps lack UTC timezone suffix — contract violation

## Title
`REPORT.md` documents all timestamps as ISO-8601 UTC strings ending with `Z` (e.g. `"2026-04-02T10:00:00Z"`). The actual serialized values have no timezone info (e.g. `"2026-04-02T10:00:00"`), violating the documented contract.

## Environment
- `app/models.py` — `utcnow()`
- All endpoints returning `started_at`, `finished_at`

## Steps to Reproduce
1. POST `/sources` then POST `/collect-runs`.
2. Inspect the `started_at` field in the response.

## Expected
```json
{ "started_at": "2026-04-02T10:00:00Z" }
```

## Actual
```json
{ "started_at": "2026-04-02T10:00:00" }
```

`datetime.utcnow()` returns a **naive** datetime object. Pydantic serializes it without a timezone suffix.

```python
# models.py line 11-12
def utcnow() -> datetime:
    return datetime.utcnow()   # naive — no tzinfo
```

## Impact
API consumers (the operator UI or any integration) cannot distinguish naive timestamps from local time. If the system clock's local timezone differs from UTC, clients may misinterpret times. Additionally, Python 3.12+ deprecates `datetime.utcnow()`.

## Severity / Priority
**Medium / P2** — API contract violation; affects any timestamp-sensitive UI logic (e.g. run duration display, FloodWait resume-after).

## Fix Suggestion
```python
from datetime import datetime, timezone

def utcnow() -> datetime:
    return datetime.now(tz=timezone.utc)
```
Pydantic will then serialize as `"2026-04-02T10:00:00Z"`.
